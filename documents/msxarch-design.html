msxarch: loading cartridge ROMs into RAM

How the MSXPi server identifies a ROM, rewrites its bank switches, and how the MSX runs the result from memory-mapper RAM instead of a cartridge slot.

branch fix/msxarch-1942 · msxarch.com 4867c04 · mapper_detect.py 07fdd4a

1Pipeline

msxarch is split so that each side does what it is good at. The Raspberry Pi has the whole ROM in memory and a fast CPU, so it does identification and patching. The MSX only stores blocks into RAM, installs small resident handlers, and jumps into the game.

MSXmsxarch.com lists ROMs from paths in MSXARCH.INI; user picks one

The MSX sends the addresses of its own handlers with the selection, so the server patches CALLs to exactly the addresses the client will use; client and server cannot drift apart. An old client that sends none gets DEFAULT_HANDLERS.

2ROM identification

Identification decides everything downstream: which windows get patched and how the MSX lays out memory. A wrong type means every switch goes to the wrong window, so the design puts an authoritative source first and heuristics last.

Layer 1 — openMSX software database (authority)

share/softwaredb.xml from the openMSX fork is indexed by SHA-1 of the whole ROM (load_romdb, a regex scan because it runs on a Pi). Location comes from ROMDB in msxpi.ini; a URL is cached locally and refreshed every ROMDB_CACHE_DAYS, and a failed refresh keeps the cached copy.

Layer 2 — detection (fallback only)

For ROMs the database doesn't list, detect_mapper counts every LD (nn),A target (32 lo hi) and runs an ordered chain on exact addresses:

9000h present              → Konami SCC   (only SCC games write it, 12–26 times)
8000h AND A000h            → Konami4
6800h or 7800h             → ASCII8
5000h / 6000h / 7000h      → ASCII16      (owns no address of its own: elimination)

If that finds nothing, a repetition heuristic takes over: an address inside a window written at least 8 times (REPEAT_MIN) is a genuine register, a coincidence appears once or twice. BUBBLE writes 7FF8h 133 times and ISHTAR 77FFh 97 times without ever touching an exact address. Both 8K halves of a 16K group in use means ASCII8; a single repeated window means ASCII16 (ANDROGYN writes only 77FFh).

Detection is exact, patching uses ranges, on purpose. In detection one false hit changes the answer for the entire ROM, so specificity wins; widening the first test to ranges reclassified 23 of 33 megaROMs as ASCII8. In patching the type is already known, a missed switch is fatal and a stray patch is local, so coverage wins. Against the 33 test megaROMs the strict chain agrees with softwaredb.xml on 32; SUPERLOA uses an unsupported mapper and is correctly left unrecognised.

3Loading and runtime on the MSX

A cartridge switches banks by decoding a write to a register. In RAM there is no such decoder, so msxarch replaces each write with a call to a handler that remaps memory-mapper segments (ports FCh–FFh).

The 8K problem and the pair cache

The MSX memory mapper works in 16 KB pages; Konami and ASCII8 games switch 8 KB banks, so one 16 KB page can hold any combination of two banks. msxarch builds a composite segment for each (low bank, high bank) pair the game actually uses:

  • Each 16 KB page (4000h, 8000h) has a cache of up to 12 segments (PAIR_CACHE_ENTRIES), allocated after the ROM segments.
  • First use of a pair copies both 8 KB banks into a victim segment with two LDIRs; later uses are a single OUT (FDh)/(FEh), which is cartridge speed.
  • Nemesis cycles through 10 pairs during music and the title; an 8-entry cache thrashed and played at a crawl, 12 entries play at 59 switches per second with no copies.

Handlers preserve every register and the interrupt state (read via LD A,I), restore both mapper ports, and only acknowledge the VDP when a copy was built.

Launch trampoline

Copied to C000h: it disables BIOS hooks (FD9Ah–FFCFh RST 30h → RET), calls INIT32, pushes a return address, and jumps to the header INIT at 4002h. Most games never return. Some (PENNANT, VALLEY2) return after registering H.STKE (FEDAh: F7 slot addr), the BIOS convention for “start me after all cartridges initialised”. The return path checks for F7 and jumps to the address at FEDCh; otherwise it idles with interrupts on.

4Patching engine

Mapper games: patch_bank_switches

Every plausible LD (nn),A (32 lo hi) whose target lies in a bank-select window becomes CALL handler (CD lo hi) — same length, no relocation, A still carries the bank number.

After examining a store, the scanner steps over the whole 3-byte instruction instead of advancing one byte, so an operand can never be re-read as a new opcode.

Plain ROMs: neutralise_rom_writes

A cartridge silently ignores writes into its own ROM; in RAM they succeed and corrupt the game. The server traces code from the header INIT/STATEMENT/DEVICE entries (following jumps, calls, BIOS-hook installs and pushed return addresses), then NOPs out traced stores whose target lies in the image — absolute stores and ld hl,nn followed by writes through (HL). Only traced instructions are touched, so data is never altered. 8 KB images are doubled so the 6000h mirror exists.

7Does the patching generalise?

Largely yes, within a clear boundary. The rules are about how Z80 code switches banks, not about particular games, and each was validated against the full test set. A Konami, Konami SCC, ASCII8 or ASCII16 game you haven't tried is likely to work if it:

  • switches banks with LD (nn),A, preceded by something that sets or preserves A — the dominant idiom in commercial games;
  • uses no more distinct 8K pairs per page than the cache holds (12) during tight loops;
  • fits in the available mapper RAM plus cache segments;
  • doesn't rely on SRAM, sound hardware on the cartridge, or reading back bank registers.

It will not catch switches written any other way:

  • ld (hl),a, ld (de),a, ld (ix+d),a with the register address computed or loaded at runtime;
  • switch code copied to RAM and executed there, or generated/self-modifying code;
  • LD (nn),A preceded by an instruction outside the accepted set (the next PENNANT-style case);
  • data that happens to pass the plausibility rules and target a window (a wrong patch, much rarer now).

Static byte patching can never be complete: whether a byte is code, and what address a computed write targets, is not decidable in general. Each new failure is cheap to diagnose with the tooling used here (openMSX watchpoints on mapper ports, comparison with the cartridge), and usually fixes as one more general rule plus an offline all-ROM diff.

Hardware path — complete

The only route to effectively every cartridge game is to stop patching and emulate the mapper decoder in hardware: MSXPi's CPLD (or an FPGA) presents a cartridge slot, decodes bank-register writes exactly like the original board, and maps pages to SRAM that the Pi filled with the ROM. The game runs unmodified, so indirect writes, self-modifying code and register reads all work; the database only has to select the decoder. Sound chips and flash-backed SRAM still need dedicated logic, which is how existing flash cartridges reach near-total compatibility.

Recommendation: keep the software loader for the large, common Konami/ASCII library, where it already works well. Add trace-based detection of indirect writes and a small override table as the next steps. Treat 100% coverage as a hardware feature, not a patching goal.
